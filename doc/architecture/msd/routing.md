# Routing Engine (RouterCore)

`src/msd/routing/RouterCore.js` is the pathfinding engine behind every MSD line: one instance per MSD card (created by `MsdCardCoordinator`), shared by all line overlays on that card. It decides each line's viewBox-space geometry — where it bends, how it avoids obstacles, and how multiple lines coordinate into bundles ("cable raceway" behavior).

User-facing behavior and configuration: [Line Routing & Channels](../../cards/msd/routing.md). This page covers the internals.

RouterCore has **zero DOM dependencies** — it's pure geometry and graph search, which is what makes it unit-testable: `tests/routing/*.test.js` (`npm run test:routing`, Node's built-in test runner) exercises it directly through a small harness (`tests/routing/helpers/router-harness.js`).

---

## Request Lifecycle

0. `buildRouteRequest` resolves the line's mode: explicit `route:` wins, then a card-wide `default_mode` (if set to something other than `auto`), otherwise `auto` resolves straight to `smart` — unconditionally, not gated on obstacles/channels being present. `manhattan` and `grid` are the explicit, always-honored opt-outs (never silently re-upgraded) for the cheap/non-participating and no-refinement-pass alternatives respectively.
1. `AdvancedRenderer.render()` positions control overlays, waits for their DOM to settle, then resolves every overlay's anchor/attachment points.
2. **Discovery loop** (`AdvancedRenderer._discoverLineRoutes`): before anything renders, every line is routed — iterated in a **fixed order sorted by overlay id, not YAML order** — repeatedly, until a full sweep causes zero registry mutations (capped by `trunk_discovery_max_passes`). This is what makes bundling outcomes independent of declaration order. The loop must use the same *complete* anchor set (static + attachment-manager virtual anchors) the render pass uses — with bare static anchors, control-anchored lines silently fail to resolve and the loop no-ops.
3. **Render pass** (Pass 2b, declaration order for SVG z-ordering): each `LineOverlay.render()` calls `RouterCore.buildRouteRequest()` + `computePath()` — all cache hits once the loop has converged.
4. `computePath` dispatches on mode: `manual` / `direct` / corridor-chained (`_computeCorridorRouted`) / plain A* (`_computeGrid`, plus `_refineSmart` for `smart`).
5. After geometry is final (post corner-rounding, pre smoothing), the line's straight runs are **registered** into the shared registries, making its geometry visible to other lines' future routing decisions.

## Core Data Structures

| Structure | Contents | Purpose |
|---|---|---|
| `_trunks` | Trunk rows: bounds, `direction`, `origin` (`channel`/`discovered`), `sourceLineId` (creator), `crossCenter`, `members: Map<lineId, [flowLo, flowHi]>` | Bundling. Config channels are pre-seeded rows; discovered rows are created from lines' own straight runs (≥ `trunk_min_length`) |
| `_crossings` | Per-line straight-run records (≥ `crossing_min_length`) | Crossing avoidance occupancy |
| `_registryVersion` | Counter bumped **only on real registry mutations** | Folded into the route cache key — the mechanism that makes the discovery loop converge and steady state free |
| `_cache` | LRU route cache keyed on every request field + `_registryVersion` + viewBox + obstacle version | A line recomputes exactly when something it depends on changed |

## A* and Cost Biases

`_computeGrid` runs 4-direction A* over a coarse grid (`grid_resolution`) with a turn penalty, plus three per-cell bias layers looked up during the search. When `grid_resolution` isn't set in config, `_defaultGridResolution()` derives it from the viewBox's own shorter dimension (~1/12th of it, clamped to `[16, 64]`) rather than a flat number — a fixed default is only ever right by coincidence, since it depends entirely on how large the author's `view_box` happens to be. Recomputed from `this.viewBox` on every call rather than cached, so it stays correct across `setViewBox()`; explicit config always wins.

- **Channel bias** (`_buildChannelCostGrid`): discount for moving *along* a prefer channel's flow direction; penalty inside avoid channels. A prefer discount can break the Manhattan heuristic's admissibility, so those searches fall back to h=0 (Dijkstra).
- **Crossing penalty** (`_buildCrossingCostGrid`): penalizes moving *orthogonally* through another line's registered segment. Always non-negative, so no admissibility concerns. **Bundle-mates are exempt** — lines sharing a trunk, and (prospectively) the occupants of a corridor being joined (`_crossingExemptIds` on corridor legs) — because reaching an outer lane legitimately crosses inner lanes, and penalizing that made A* sneak around segment endpoints instead.
- Cardinal `anchor_side`/`attach_side` guarantees are enforced *structurally* with fixed stub segments spliced around the search (`_applyCardinalStubs`), not as costs — see below for how long that stub is allowed to be.

## Corner-Radius-Driven Stub Length

`_applyCardinalStubs` and `_computeManhattan`'s own fallback stub logic both splice a **fixed, unsearched** lead-out/lead-in segment onto the true endpoint before any A*/crossing-cost evaluation runs — the pathfinder only ever searches between the *stub* endpoints. Reserving a large radius-driven length here (historically always `2 × cornerRadius`, so corner rounding always had room to render in full) means that length can never be routed around anything, including another line's already-registered crossing segment, regardless of `crossing_avoid_bias` — a structural precedence of corner geometry over crossing avoidance, not a cost tradeoff a bias knob can influence.

Two functions split this:

- `stubLengthFor(req)` — the corner-radius-driven length (`max(MIN_STUB_LENGTH, cornerRadius*2)`), gated on `cornerStyle` actually rendering an arc/chamfer (`round`/`bevel`; a `miter` line has nothing to make room for). Used unconditionally by `_pushBundledApproachLegs`'s bundled-corridor lane-nudge distance — that leg is independently pathfound through the crossing-cost grid inside `_computeCorridorRouted`'s leg loop, so it isn't a blind splice, and shrinking it has its own previously-confirmed, unrelated regression (near-sharp bundled-lane corners; see that function's own comment).
- `cardinalStubLengthFor(req, minAutoLength)` — used only by the two genuinely blind call sites (`_applyCardinalStubs`, `_computeManhattan`'s fallback). Checks `req.stubLength` first (an explicit per-line override, see below) and returns it unconditionally (floored at 0) if set. Otherwise returns `stubLengthFor(req)` when `req.cornerRadiusMode === 'forced'` (opt-in, matches pre-2026.07 behavior exactly); otherwise (`'auto'`, the default) returns `minAutoLength` (the router's own resolved `grid_resolution`), leaving the full route shape — including whether/where to depart — to the crossing-aware search. Rendered corner radius still targets the configured value wherever the chosen path's own leg lengths allow it (`_applyCornerRounding`'s existing per-corner clamp is unaffected by any of this).

`cornerRadiusMode` is a static per-request field resolved in `buildRouteRequest` exactly like `cornerRadius`/`cornerStyle` — no new stored state, nothing touching `_trunks`/`_crossings`/`_registryVersion`/lane assignment directly, and it's folded into `_cacheKey` (`CRM:`) alongside the existing `CR:`/`CS:` fields.

**`stub_length` override**: a line overlay can set `stub_length` (viewBox units) to bypass both the `auto`/`forced` computations above entirely — read in `buildRouteRequest` as `req.stubLength`, consumed first by `cardinalStubLengthFor`. Useful for one line that needs a specifically shorter or longer mandatory lead-out than its `corner_radius_mode` would otherwise produce, without touching the card-wide `grid_resolution`.

**Stroke-width-aware corner clearance**: `buildRouteRequest` resolves `req.width` from the line's own style (`style.width` / `style.stroke_width`, mirroring `LineOverlay`'s own resolution order, default `2`) and threads it through `_registerLineSegments` into each registered `_crossings` entry. `_distanceToNearestOtherLineSegment(p, askingLineId, askingWidth)` nets `(askingWidth + otherWidth) / 2` off the raw centerline-to-centerline distance before `_applyCornerRounding` clamps a corner's radius to it — so two thick parallel lines get a smaller effective radius at the same lane spacing than two thin ones, correctly accounting for their rendered edges rather than their centerlines. This is what fixed a previously-reported visual artifact: at high stroke width, the *outer* edge of a rounded corner curved fine but the *inner* edge rendered squared-off — an unavoidable SVG-stroking fact once the radius is less than roughly half the stroke width, which the old centerline-only clearance calculation didn't account for. `width` participates in the "did this registration actually change" diff alongside the segment's endpoints, so a width-only edit still bumps `_registryVersion` correctly.

**Corner-room refinement (`corner_room_weight`, on by default) — a different tool from the stub reservation above, deliberately.** This section's own stub-length mechanism is a *blind, structural* reservation: `2 × cornerRadius` is carved out unconditionally before the search runs, whether or not there's actually a cheaper route that also happens to leave room for the corner — and that bluntness has a documented cost (`cardinalStubLengthFor`'s own docblock, `RouterCore.js:71`, notes `_pushBundledApproachLegs`'s bundled-corridor lane nudge deliberately does NOT use the cheaper floor for exactly this reason — shrinking that reservation has its own previously-confirmed, unrelated regression: near-sharp bundled-lane corners). `corner_room_weight` takes the opposite approach for *interior* corners (the ones this stub mechanism never reaches at all — see below): it's a *cost-compared* local refinement, reusing `_refineSmart`'s existing elbow-nudge search (previously gated solely on `smart_proximity > 0`, now also triggered by `cornerRoomWeight > 0 && cornerStyle === 'round' && cornerRadius > 0`). A new helper, `_estimateCornerRadii(pts, radiusGlobal, routeId, ownWidth, { skipNeighborClearance })`, was extracted from `_applyCornerRounding`'s own pre-calc + consecutive-corner-adjustment logic (mechanically, zero behavior change to `_applyCornerRounding` itself) so refinement scoring and final rendering share one source of truth for "how would this corner round" — refinement uses `skipNeighborClearance: true` to skip the expensive 20-iteration binary search against other lines' segments (leg length dominates in the tight-detour shapes this targets), but always runs the consecutive-corner-adjustment pass, since skipping *that* would make the estimate under-report shortfall in exactly the cases this feature exists for.

Each elbow-shift candidate's cost gets `+ shortfall * cornerRoomWeight` added, where `shortfall` is the sum (not max — a single shift can change up to 3 corners at once) of `max(0, cornerRadius - achievedRadius)` across the candidate's own corners, computed the same way for the *baseline* (unmodified) path before the search starts and carried through exactly like `penaltyBefore`/`bestPenalty` already are for `smart_proximity`'s proximity penalty — omitting that baseline term was the one real bug caught in this feature's design review: without it, every candidate is compared against a baseline that silently pays zero shortfall cost, making a genuine improvement over a badly-squashed original corner still lose to that original's phantom "shortfall=0" score.

**A pre-existing, independent bug this work surfaced and fixed**: `_refineSmart`'s elbow-shift candidate generation used to move a *single* point to explore a detour. For an elbow with one fixed neighbor on each side, no single-point move can preserve orthogonality on *both* adjacent legs simultaneously — moving along either axis necessarily leaves the untouched leg's far endpoint fixed, producing a segment that changes both x and y at once (a diagonal, structurally invalid for this Manhattan-only router). This was always true, for any elbow shift regardless of what triggered it — but `_refineSmart`'s own elbow-shift loop was rarely exercised (gated behind `smart_proximity`, off by default, low real-world usage) and neither `_compactPolyline` (only removes collinear points) nor `_costComposite` (a plain sum, never axis-aware) ever checked for it, so a diagonal candidate could be silently accepted and rendered. Reproduced with `smart_proximity` alone, `cornerRoomWeight: 0` — confirming it predates and is independent of this feature; `corner_room_weight` shipping on by default is simply the first thing to exercise the elbow-shift loop broadly enough to make it visible.

A first fix attempt (reject any candidate whose compacted result contains a diagonal, rather than repair it) was tried and reverted: for a genuine 90° corner, of the 4 candidate shift directions, exactly 2 are geometrically capable of producing a valid result at all (the other 2 slide along a leg's own existing axis and always degenerate to a no-op once compacted) — but even those 2 still produced a diagonal with the OLD single-point-move code, so a reject-only guard made the entire elbow-shift mechanism a permanent no-op for *either* trigger (`detoursAccepted` stuck at 0 even at an artificially large weight/span, confirmed via direct instrumentation).

**Actual fix — proper geometric repair, not rejection**: candidate generation now only produces the 2 geometrically-meaningful shift directions per elbow (dropping the 2 that can only ever degenerate), and each one is a genuine 2-point replacement — the shifted corner plus one corrective point — instead of a 1-point move, so both adjacent legs stay orthogonal by construction. For a `verticalIn`/`horizontalOut` (└/┌-shaped) elbow, shifting along Y keeps the incoming leg vertical and the corrective point (at `next.x`, shifted-Y) keeps the new row until stepping back down to `next`'s own y; `horizontalIn`/`verticalOut` is the exact mirror on X. This legitimately adds one bend by design (exactly what `smart_max_extra_bends` already exists to cap), not by defect.

Two further safety checks were added once candidates started actually getting accepted and exposed them live: (1) each candidate's own compacted path is checked with `_segmentCrossesObstacle`/a same-axis-reversal check before it's eligible for acceptance at all — a bump can legitimately swing through where an obstacle happens to sit, or backtrack against the route's established flow, and there's no single well-defined "fix" for either, so these are rejected outright, never repaired. (2) A **separate, unrelated gap** these accepted candidates exposed: `_computeCorridorRouted`'s own leg loop falls back to the never-obstacle-aware `_computeManhattan` when both `_computeGrid` and its existing relaxed-hint retry (see "Corner-Radius-Driven Stub Length" above) fail — normally safe, since that combination failing usually means no path exists either way, but a corridor cursor/entry point isn't necessarily a line's own true anchor/attach, and one can end up geometrically *inside* an unrelated obstacle once corner-room refinement shifts where a trunk it belongs to must be reached from (a configuration `_computeGrid`'s own goal-cell exemption wasn't designed for — see `_pointInsideObstacle`'s own docblock). Confirmed as a real, live regression (a line rendered straight through a control it had correctly avoided before); fixed by checking the Manhattan fallback's own result for obstacle-crossing and rejecting the whole corridor candidate if so — mirroring this same function's existing entry/exit `_pointInsideObstacle` check — so `computePath`'s corridor-vs-plain comparison falls back to the plain route instead, which has no dependency on the shifted trunk position.

**A third safety check, found later**: none of the above ever validated a candidate against the card's own declared `viewBox`. Confirmed as a real, live bug: a plain route (no channel involvement at all) rendered a point outside the viewBox entirely — a large enough corner-radius shortfall elsewhere in the same path made an off-canvas elbow shift look like a genuine cost improvement, since nothing in the comparison had any notion of "off-canvas" being worse. Fixed by adding a `viewBox`-bounds check to the same rejection loop as the obstacle-crossing/reversal checks above — reject outright, never repair, for the same reason those two do: there's no single well-defined "pull it back onto the canvas" fix. Covered by `tests/routing/refine-smart-viewbox-bounds.test.js`.

## Per-Waypoint Corner Radius Override

`manual`-routed lines can override an individual corner's rounding radius (`round`) or chamfer size (`bevel`) via a 3rd number on a coordinate waypoint (`[x, y, radius]`), instead of every corner sharing the line's single `req.cornerRadius`. This is a *target substitution*, not a parallel mechanism: `_estimateCornerRadii` already computed a per-corner radius internally (room clamp, neighbor-clearance shrink, consecutive-corner scaling — see "Corner-Room Refinement" above) from one global scalar; a per-waypoint override just replaces which value each corner's clamp chain starts from, via a new `perCornerRadius` option (`perCornerRadius[i-1]` for the corner at `pts[i]`, `null` = inherit `radiusGlobal`) — everything downstream is unmodified and still applies as a ceiling over whichever target is in effect. `_applyCornerBeveling` does **not** share `_estimateCornerRadii` (its own separate, simpler pre-pass — no neighbor-clearance search) and needed the identical one-line substitution independently.

**Carrying the radius through `_computeManual`'s point pipeline**: a waypoint's own radius must travel *with* its point, not be re-derived by index after the fact — `_computeManual` can silently drop a waypoint (malformed array, unresolvable named anchor) or dedup it against a coordinate-identical neighbor, either of which would misalign a naive `perCornerRadius[k] ↔ req.waypoints[k]` index mapping. `_computeManual` instead builds `{pt, radius}` entries, dedupes on `pt` (merging a later duplicate's non-null radius onto the surviving point rather than losing it), then splits into the existing `pts` array (unchanged shape — dozens of call sites assume `[x,y]` tuples) plus a new `perCornerRadius` array sized to interior points only. Named-anchor waypoints (`"anchor_name"`) can't carry a radius (not arrays) and always resolve to `radius: null`.

Scoped to `manual` mode only: `result.perCornerRadius` only exists on `_computeManual`'s return value, so every other mode (`grid`/`smart`/`direct`/corridor-routed) passes `null` into `_applyCornerRounding`/`_applyCornerBeveling`, identical to pre-existing behavior.

**Cache-key gap this surfaced**: `_cacheKey` never included `req.waypoints` at all — only endpoints, mode, corner scalars, smoothing, viewBox. A per-corner radius edit is exactly the "endpoints unchanged, interior state changed" case that risks a stale cache hit, and `LineOverlay.js` calls `computePath` with no explicit `invalidate()` of its own to cover the gap (unlike `ShapeOverlay.js`, which already worked around it for polyline point edits — see below). Fixed by folding `JSON.stringify(req.waypoints)` into the key (empty string for every non-manual line, since `buildRouteRequest` always sets `waypoints: []` for those — effectively a no-op on the overwhelming majority of cache keys).

**Adjacent bug found and fixed in the same pass**: `invalidate(id)`'s brute-force scan checked `k.includes('@${id}|')` against keys shaped `${req.id}@${x1},${y1}-...` — `id` is followed by `@`, never preceded by it, so that substring never matched any real key. `invalidate(<specific id>)` was a dead no-op wherever it was called (`ShapeOverlay.js`'s own interior-point-edit staleness guard, `AdvancedRenderer.js`'s anchor-moved guards — the latter likely masked in practice since a moved anchor also changes `a`/`b`, producing a naturally different key anyway). Fixed to `k.startsWith(`${id}@`)`.

## Confirmed Architecture: Channel Entry Is Always At An End

A user asked directly whether a line can enter a channel *partway through its span, from the side* — running mostly parallel for most of the channel's own length rather than travelling its full flow-axis extent. Confirmed, by reading `_channelCrossingPoints` directly: no. `entryFlow = Math.max(lo, Math.min(hi, approachFlow))` always clamps to within `[lo, hi]` (the channel's own flow-axis bounds), and whenever the approach point sits outside that range — the common case — it snaps to the *nearest boundary*, one of the channel's own two ends. There's no code path that lets a line join a channel's own centerline mid-span from the side; every crossing is an end-to-end (or end-to-partway-through) traversal by construction. This is a real architectural constraint, not a bug — changing it (to allow a genuine mid-span side-entry) would be a substantial design change, not a fix, and wasn't attempted here.

**A related, deliberately-unresolved tension, found while investigating a live report of this same behavior**: chaining a line through a `mode: prefer` channel whose own crossing is *degenerate* (entry === exit, e.g. because the channel's own bounds don't reach the line's approach row) into a *second* channel positioned back toward where the line originally came from creates a genuine conflict between this file's own two established invariants — "never render a same-axis reversal" (see "Corridor-Crossing Direction Enforcement" and "First-Hop-Degenerate Chain Reversal" above) and "never force a detour when a direct path exists." Confirmed empirically: forcing the direct (but reversing) shape reintroduces the exact literal reversal those earlier fixes exist to prevent; blocking the reversal forces an artificial sideways detour instead, since the geometry genuinely has no third option — the line touches the first channel's boundary, gains nothing from it (zero real distance travelled inside a degenerate crossing), and immediately needs to head back the way it came to reach the second channel. Neither option is a real fix, both are inherent to the corridor-chaining architecture's confrontation with a channel whose own crossing carries no real distance. Not resolved this pass — needs its own dedicated design pass (mirroring `corner_room_weight`'s own process) rather than a quick patch, given the direct conflict with already-hardened invariants. A live-reported instance of the underlying "S-detour" symptom this tension can also produce (a channel whose own end boundary sits within one `grid_resolution` of the line's own approach row, aliasing `entryAlreadyInside` to false at the exact-equality level while being true in every practical sense) was independently resolved for that specific reported config by the "A Third Safety Check" fix above, which changed the corridor-vs-plain cost comparison enough that plain wins outright — but that's this config's own escape hatch, not a fix to the underlying tension.

**A follow-up report on this exact tension confirmed it can go further than a detour — it can produce a literal self-crossing loop.** With a *third* geometry (a differently-shaped `channel_north`, still chained into `channel_1`), the "artificial sideways detour" horn of the dilemma above didn't just waste distance — a *later* leg's own segment crossed an *earlier* leg's own segment (`(526.1,660)→(526.1,540)` crossed `(432,637.15)→(974.53125,637.15)`). Root cause: `_computeCorridorRouted` pathfinds each leg of a chain independently, with zero awareness of an earlier leg's own geometry — and the channel discount (`deltaCost: -590.53` here) was large enough to win the corridor-vs-plain comparison regardless, since `_segmentCrossingPenalty` (the crossing-cost term in that comparison) only ever checks a candidate against *other lines'* registered segments, never the candidate's own earlier legs.

Fixed with `_polylineSelfIntersects`: a hard reject, not a bigger cost penalty (a penalty, however large, can always in principle be outweighed by a large enough discount elsewhere in the same candidate — precisely the failure mode here; a reject is unconditionally robust regardless of future discount tuning). Reuses the identical strict-interior perpendicular-crossing and collinear-overlap tests already established in `_segmentCrossingPenalty`, just checked against the polyline's own non-adjacent segments instead of `this._crossings`. Called at the end of `_computeCorridorRouted`, after both `_collapseSoftLegReversals` and `_compactPolyline` run (confirmed via design review: a legitimate bundled-lane "bump" shape can only even resemble a false positive in a case `_compactPolyline` always collapses away first), gated `!hasForceChannel` — the identical gate this function's own `_pointInsideObstacle` rejection already uses, for the identical reason (force channels are mandatory by explicit user config, never silently overridden). `computePath`'s own corridor-vs-plain comparison already treats a null candidate as simply unavailable and falls back correctly.

This resolves the *symptom* (a self-crossing loop can no longer win the comparison) without resolving the *tension* documented above (reversal-vs-detour, for a chain through a near-zero-benefit degenerate crossing) — that still needs its own dedicated design pass if a live config surfaces it again in a form this reject doesn't happen to route around. **Known, accepted scope limit**: `hasForceChannel` gates the whole chain, so a mixed force+prefer chain whose self-crossing is caused entirely by the optional prefer leg's own geometry still ships unfixed — matches the existing `_pointInsideObstacle` precedent exactly, not a new inconsistency. Covered by `tests/routing/corridor-self-crossing.test.js`.

## Post-Search Reshape — Orthogonality Invariant

After `_computeGrid`'s A* search reconstructs a path, a final reshape pass snaps the first and last segments onto the exact requested endpoint coordinates (the search itself only ever lands on grid-quantized points). Each side has a **degenerate-axis relief**: when the *required* axis for that end has zero real distance to cover (e.g. a `channel_axis` hint wants vertical, but start/end already share the same y), forcing the segment onto that axis anyway would insert a spurious zero-length elbow — so the relief accepts the reconstructed segment as-is instead.

That relief had a latent gap on both the first-move and last-move sides: it accepted the segment as "already correct" purely from the required axis being degenerate, **without first confirming the segment was orthogonal at all**. Under specific grid-snap geometry (confirmed via direct leg-level instrumentation, not hand-derived) the raw reconstructed segment could be genuinely diagonal — both x and y changing on one segment, structurally impossible for this Manhattan-only router to render or corner-round correctly — and the relief waved it through untouched instead of falling to the pre-existing, already-correct "genuinely diagonal" corrective-elbow logic one branch below. Fixed by requiring `orthogonal = actuallyHorizontal || actuallyVertical` as a precondition on both sides before the degenerate-axis relief can declare a segment "already correct."

This invariant — **every segment `_computeGrid` produces must be axis-aligned** — is asserted directly in `tests/routing/diagonal-segment.test.js` via the harness's `findDiagonalSegment(pts)` helper (distinct from `findIllegalReversal`, which only ever examines already-orthogonal segments; a diagonal segment is a strictly worse, rendering-breaking defect, not a visual wobble). Fixing this also incidentally resolved an unrelated-looking complaint — a line taking a marginal, visually-awkward detour through a second barely-qualifying trunk instead of riding a single clean one — because the corrupted intermediate leg geometry had been making a worse routing candidate look artificially competitive during cost comparison.

**Bend/segment counting**: `meta.bends`/`meta.segments` (and the internal cost function's own bend count, `_costComposite`) are derived from `_compactPolyline(pts).length`, never raw `pts.length` — a collinear "phantom" point (most commonly a mandatory stub's landing point continuing in the same direction the route already had) otherwise over-counts by one per occurrence. `_compactPolyline` still deliberately preserves genuine same-axis reversal points (see Convergence Discipline below), so this only removes true pass-through points, never a real bend.

### Same-Grid-Cell Collapse and the Generic Reshape Branch

A leg whose raw `req.a`/`req.b` round to the *same* grid cell (e.g. an interior corridor hop shorter than one `grid_resolution`) makes the A* search "arrive" on its very first pop — reconstruction produces one degenerate point, which an existing guard duplicates before the reshape snaps both copies back onto the two real, distinct `req.a`/`req.b` coordinates. Each reshape side's **hard-hint branches** (`channel_axis`/`continuation`) were already fixed, earlier this session, to test the *current*, post-snap segment directly for exactly this reason — the alternative, `origStart`/`origEnd` (the grid's own *pre-snap* reconstructed point), is for a same-cell collapse just the single collapsed cell's own center, unrelated to either real endpoint.

The **generic branch** (no hard hint on that end — `geometry`) was never given the same treatment, and could overwrite an already-correct, already-snapped 2-point orthogonal segment based on that same stale `origStart`/`origEnd` comparison — collapsing it into a single repeated point, which rendered as a diagonal once concatenated with the preceding splice (the stub, or another leg's own endpoint). Confirmed live: a corridor chain with a short interior hop into a channel boundary produced exactly this.

**First fix attempt, reverted**: testing the current segment directly, unconditionally, in the generic branch. This broke the *normal* (non-collapsed) case instead — there, the pre-adjustment `pts[lastIdx-1]` is the grid's own *unsnapped* rough corner, which essentially never exactly matches the already-snapped `req.b` on either axis, so an unconditional "already orthogonal" check fails almost every time, turning many previously-fine legs into unnecessary corrective-elbow insertions (confirmed via the full regression suite: 4 real failures across unrelated scenarios in `diagonal-segment.test.js`, `trunk-mate-overlap.test.js`, and others).

**Actual fix**: capture `wasSameCellCollapse` once, at the exact point the existing guard duplicates the collapsed point, and gate a *separate*, narrow branch on it — testing the current segment directly *only* for the collapsed case; the original `origStart`/`origEnd`-based heuristic is completely untouched for the normal case. Covered by `tests/routing/same-cell-collapse-diagonal.test.js`.

## Corridor-Crossing Direction Enforcement

A `channel_axis`-sourced hint's hard block in `_computeGrid`'s neighbor-expansion loop (as opposed to the post-search reshape above, which runs after the fact) guarantees a leg's departure from — or arrival at — a corridor crossing lands on the *required axis*: `if (isHorizontalMove !== req._channelAxisHorizontalFirst/Last) continue;`, on both the first-move and last-move sides. That's an axis check only — it says nothing about *which* direction along that axis, even though a `continuationDir` (the corridor's own known flow direction, e.g. "must arrive moving rightward, not leftward") is frequently available on the same request (`req._continuationDirFirst`/`Last`, populated by `_computeCorridorRouted`'s own `entryHint`/`departHint` construction whenever a channel's flow direction is already known).

Confirmed as a real, live bug: a line chained through a single `mode: prefer` channel via `route_channels` rendered a same-axis reversal right at the channel's own entry boundary. The mechanism has two parts, neither sufficient alone: (1) the axis-only block let the search satisfy "must be a horizontal arrival" while still arriving from *either* side — including the exact reverse of the channel's configured flow; (2) `_buildChannelCostGrid`'s per-cell 'prefer' discount applies to any leg carrying the channel in `req.channels` (the line's own `route_channels`), not just the leg specifically designated as the official crossing — so the *approach* leg (still technically outside the channel) already earns a reward for cells inside the channel's own bounds, making it look artificially cheap to wander in early and correct course afterward rather than approach the entry boundary directly. Combined, the search found "overshoot into the channel, then arrive at the entry moving backward against the flow" cheaper than a direct approach.

Fixed by extending the existing axis-only block, on both sides, to also block the exact reverse of `continuationDir` when one is known — mirroring the identical, already-present pattern used for the *degenerate*-axis case immediately adjacent to it (and for the plain `'continuation'` hint source elsewhere in the same loop), rather than inventing a new mechanism. The broader channel-bias scoping (approach legs earning credit for a channel they haven't officially entered yet) is a separate, known architectural characteristic, not narrowed by this fix — only the direction gap that let it render as an actual reversal is closed. Covered by `tests/routing/channel-entry-direction.test.js`, reproduced through the full multi-line discovery loop (an isolated single-line `computePath` call does not trigger it — the exact cross-line interaction that tips the grid search into the buggy shape wasn't further isolated, since the fix itself is verified correct and general regardless). *(That "separate, known architectural characteristic" resurfaced almost immediately at a different call site — see "Plain-Candidate Channel-Bias Leak" immediately below, which does narrow it, at least for the specific case that bit next.)*

### First-Hop-Degenerate Chain Reversal

`_computeCorridorRouted`'s chain loop tracks `prevChannelDir` — the last known real direction of travel — specifically so a leg departing a channel whose own entry→exit crossing was *degenerate* (zero real distance, `entry === exit`, e.g. because the channel's own bounds don't reach the line's flow-axis range) still gets a "don't reverse" guarantee instead of none at all. That mechanism works by carrying a real direction *forward* from an earlier channel in a chain — but had no fallback when the very **first** channel in the chain is itself the degenerate one: there's no earlier channel to carry a direction from, so `prevChannelDir` silently stayed at its initial `0`, and the **second** channel's own approach leg departed with zero reversal protection.

Confirmed as a real, live bug: a line chained through two `mode: prefer` channels (`route_channels: [channel_north, channel_1]`) rendered a same-axis reversal departing `channel_1`'s own approach leg — overshooting back the way it had just arrived from `channel_north` before continuing on. Fixed by deriving a fallback direction, when `k === 0` and `continuationDir` is `0`, from the approach leg's own real displacement (`cursor` before this channel's reassignment, to `entry`) — the same real, known fact the entry hint already hard-blocks the leg to arrive via, just not previously read back out. Covered by `tests/routing/channel-chain-first-hop-degenerate.test.js`.

## Plain-Candidate Channel-Bias Leak

`computePath`'s prefer-channel/discovered-trunk branch compares a `plain` candidate (the honest, no-corridor route) against every corridor option on `effectiveCost` (`meta.cost` + a crossing-avoidance tiebreaker) — see "Trunk-and-Branch" below for why per-option comparison exists at all. `plain` was computed as `_computeGrid(stubReq, {smart:true})` (then `_refineSmart`), and `stubReq` is just `{...req, a: p1s, b: p2s}` — it still carries the line's own `req.channels` through completely unmodified. `_computeGrid` unconditionally builds a per-cell channel cost bias from whatever `req.channels` names (`_buildChannelCostGrid`), for *any* call using that request — so `plain` was never actually channel-blind: it received the same 'prefer'-mode discount for wandering into the channel's bounds as a genuine corridor leg would, even though `plain` by definition never uses the corridor mechanism at all (`channel.coveragePct` stayed `0` on the resulting route).

Nothing makes a detour-for-an-unrealized-discount shape actively *cheaper* on its own — a route with more bends is still a route with more bends. Confirmed as a real, live bug once a user lowered `turn_penalty` (the flat per-move A* search cost for a direction change) from its default of `2` down to `0.5` while tuning corner appearance: with bends nearly free, the plain candidate's phantom channel-discount detour became net-cheaper than the honest direct shape — even though the detour crossed a *completely unrelated* line's own route twice. (The tight, unroundable ~90° corners the user also noticed at the crossing points are a downstream symptom, not a separate bug: `_estimateCornerRadii`'s neighbor-clearance clamp correctly shrinks a corner's radius near another line's registered segment, which mechanically happens right at a crossing.)

Fixed by giving `computePlain()` its own request: any channel id present in `explicitCorridors` (i.e. any `force`/`prefer` channel this line could actually chain through) is stripped from `req.channels` before it reaches `_computeGrid`/`_refineSmart`, so the comparison baseline is an honest "what if this line never used the channel at all" — matching what the surrounding cost comparison already assumes it's comparing. `avoid`-mode channel ids are deliberately left in place: they're never chained into `explicitCorridors`, so their repulsion bias is exactly what an honest plain route should still respect regardless. When no competing line creates a crossing risk, the corridor can still legitimately win the comparison outright (confirmed: a real, non-zero `coveragePct`, `strategy: 'corridor-routed'`) — that's a deliberate, cost-vetted use of a channel the line opted into via `route_channels`, not a bug; the fix only removes the *unearned* credit the plain candidate was getting for the same channel. Covered by `tests/routing/channel-plain-candidate-bias.test.js`, both the full multi-line reproduction of the exact reported config and a minimal 2-line isolation of the mechanism itself.

## Trunk-and-Branch (Bundling)

A channel is just a **pre-seeded trunk**; a discovered trunk is a corridor learned from another line's routed path. Both live in `_trunks` and flow through the same corridor-composition machinery:

- **Discovery** (`_discoverTrunkCandidates`): a line finds joinable trunks by flow-axis overlap (≥ `trunk_min_overlap`) and cross-axis proximity (≤ `trunk_proximity`). Exclusions: corridors already referenced explicitly, trunks the line itself *created* (self-reference), ghost shells with zero members, and channel-origin rows authored with `discoverable: false`. Membership is deliberately **not** an exclusion — a joined line must be able to re-discover its own trunk on recompute, or joining would silently revert on the next recompute ("join ratchet"). Note discovery runs regardless of a line's own `route_channels` — that field only controls whether a channel is *mandatory*/cost-biased for lines that list it, not who else is allowed to discover it; `discoverable: false` is the only way to scope a channel to just its explicit `route_channels` users.
- **Composition** (`_computeCorridorRouted`): approach leg → through leg → depart leg per corridor, each leg independently pathfound. A discovered trunk (or prefer channel) chain is an *optional candidate* compared against the plain route by real cost; only `force` channels are mandatory. Force chains skip trunk discovery entirely — nothing can cost-vet an addition to a mandatory chain.
- **Discount cap** (`_trunkBundleDiscountCap`, config `trunk_bundle_discount_cap`, default `2000`): `_corridorDelta`'s `prefer`-mode discount credits at most this much distance toward a *discovered* trunk's cost reduction — a conservative architectural safety bound against an unbounded discount theoretically buying an arbitrarily complex local detour, scoped to `origin: 'discovered'` only (a `force`/`prefer` channel the user authored via `route_channels` is never capped). Generous enough that it doesn't bind on any realistic or currently-tested scenario; it exists as a ceiling, not a tuning lever.
- **Registration** (`_registerLineSegments` → `_mergeOrRegisterTrunk`): a finished route's straight runs merge into geometrically-matching trunk rows as member spans, or create new rows. Registration is **diff-in-place**: matching entries update (identical geometry reports no change), and only entries the scan didn't touch are dropped. Rows are never deleted (emptied "shell" rows reactivate on rejoin).

## Lane Assignment — Derived, Never Stored

`_trunkLaneAssignment(corridor, lineId, chainSideHint)` computes `{laneIndex, laneCount, offset}` as a **pure function of the trunk's current member set** on every call. (The sections below describe each branch's *baseline* per-corridor behavior; "Chain-Aware Corridor Lane Consistency" further down covers `chainSideHint` and the same-side tie-break's own geometry-vs-lexicographic logic in full — both branches now route through the shared `_sameSideOrder`/`_bothGroundedAt` helpers described there instead of each maintaining their own copy.)

- **Discovered trunk**: the creator (`sourceLineId`) implicitly holds lane 0 at offset 0 — its path *is* the centerline (`crossCenter`). Joiners (members minus creator, plus the asking line, sorted lexicographically within each side) alternate sides: `+s, -s, +2s, -2s, …`. The row's cross-axis band width is likewise derived from joiner count (`_trunkBandHalfWidth`), grown symmetrically so the band center never drifts. The creator's own natural side (`Math.sign` of its path's own cross-axis offset from `crossCenter` at registration — normally `0`, since the creator's path *is* the centerline) is recorded per-member alongside its flow span and, when strictly positive, flips which side-group is assigned the lower `laneIndex` (positives first instead of the default negatives-first) — a lane *numbering* preference only; it cannot move any line's own already-computed path, since lane bookkeeping runs after routing, not before.
- **Config channel**: all users get centered offsets `(i − (n−1)/2) × line_spacing`, clamped to the authored band. Ordering among members is the SAME `naturalSide`-first, lineId-tie-break sort the discovered branch uses (`_mergeOrRegisterTrunk` already records `naturalSide` per member regardless of trunk origin — the config-channel branch just wasn't consulting it, pure lexicographic `[...ids].sort()` until fixed). Reported live: a shared corridor's lane ordering "is bound to create unnecessary crossovers" via lexicographic sort alone — confirmed with a constructed counter-example (an alphabetically-first line whose real destination leans one way, an alphabetically-last line leaning the other) — the old code assigned lanes exactly backwards from each line's own geometry. Covered by `tests/routing/channel-lane-natural-side.test.js`.

There is deliberately **no stored lane state**. The predecessor (`_channelLineIndex`, a permanent insertion-order map) caused the engine's recurring failure class: stateful per-corridor bookkeeping that the discovery loop couldn't converge over. Membership changes bump `_registryVersion` (lanes depend on membership), while identical re-registration is a strict no-op.

## Matched-Sibling Corner-Arc Clearance

Reported live: several lines bundled through a shared force/discovered channel, all turning the same direction as they exit it, rendered with wildly inconsistent corner radii — one line got a full, graceful arc while a neighbor got an almost-sharp corner, even though geometrically they were doing "the same turn." `corner-neighbor-trim.test.js` had already fixed the case where a neighbor's OWN corner-rounding arc had receded from a straight span still registered as sharp (`trimLo`/`trimHi`, above `_distanceToNearestOtherLineSegment`) — the remaining gap was specifically the neighbor's **curved** region, which a linear trim can't represent.

Two generic fixes (candidate-CENTER-vs-neighbor's-registered-arc, as a bounding box then as sample points) were tried and reverted: checking a candidate's center against a target is a sufficient-but-not-necessary safety proxy, and gets measurably wrong once the target is a discrete curve rather than an extended straight segment (see `tmp/ROUTING_ARC_CLEARANCE_FOLLOWUP.md`, superseded for the bundle-mate case below — the fully generic arbitrary-line version remains open, see Known Limitations).

The shipped fix is narrower and exactly solvable: it only ever engages for **bundle-mates** (lines sharing a trunk/channel row) turning the identical way at corresponding ends of the shared corridor — not arbitrary nearby lines.

- **Identification** (`_matchedTrunkCorner`, `_matchedSiblingArcs`, near `_distanceToNearestOtherLineSegment`): a corner at `pts[i]` is a trunk-exit corner when its incoming run's flow span exactly matches this line's own already-registered member entry in some `_trunks` row (read-only lookup — nothing new to compute or store beyond what registration already tracks). A sibling "matches" when it's a member of that same row with a corner registered at the same relative end (`atLo`), with an **identical `(vInUnit, vOutUnit)` pair** — not just the same `offsetDir` — since two geometrically distinct turns (e.g. arriving leftward/departing downward vs. arriving upward/departing rightward) can share an `offsetDir` while sweeping in opposite rotational senses (the `vIn×vOut` cross-product sign differs).
- **Registration plumbing** (`_registerLineSegments`'s `cornerGeomAt` map, threaded through `_mergeOrRegisterTrunk`'s new `cornerInfo` parameter into a 4th slot on the member tuple, `[flowLo, flowHi, naturalSide, cornerInfo]`): purely derived, recomputed every call from that call's own `pts`/`cornerRadii` — no new mutable state, matching the "derived, never stored" discipline above. The change-guard (`_cornerInfoEqual`) folds a corner's resolved radius and turn shape into the existing "did anything real change" comparison alongside `naturalSide`.
- **Exact clearance** (`_siblingArcClearance`): once a sibling's own corner is resolved, its full swept arc shape is fully known (not just a center point) — sampling BOTH arcs independently at K+1 angles (K=12) and taking the true minimum pairwise distance converges to the exact rendered gap as K grows. Verified against `tests/routing`'s `flattenSvgPath` oracle on the reported scenario to track true clearance within ~0.5%. Matched single-index sampling (candidate sample *i* vs. sibling sample *i*) was tried first and confirmed too loose (~13.2 vs. true ~9.55) — the true closest-approach pair between two differently-centered arcs generally sits at *different* sweep fractions on each arc.
- **Combining with the existing proxy — `Math.max`, never a replacement**: the exact signal only ever **floors up** the existing `_distanceToNearestOtherLineSegment` proxy (which still runs unmodified, against every line including matched siblings) — it never excludes or replaces that comparison. An earlier attempt excluded a matched sibling's registered segments from the proxy and relied solely on the exact check; confirmed via harness to genuinely **oscillate** (two mutually-matched siblings each reading the other's previous-pass resolved radius with no monotonic anchor, cycling between ~2.7 and ~34 indefinitely instead of converging). Flooring against the untouched, already-monotonic proxy (proven by `trimLo`/`trimHi`'s own convergence argument) restores the same guarantee: this mechanism can only ever loosen a corner beyond what the proxy alone already produced, never make it tighter, and the fixed point is a genuine one — confirmed via the harness with the pass cap raised to 20 and still converging at pass 4.
- **Convergence cost**: engaging this mechanism at all (i.e. when two trunk-mates share a matching turn shape) can add up to one legitimate extra discovery-loop pass versus before this existed — the same "a sibling's data is only visible a pass after it registers" latency `trimLo`/`trimHi` already has. Still safely within the existing pass cap in every tested scenario, including the larger bundles in `scale-stress.test.js`.

Covered by `tests/routing/matched-corner-arc-clearance.test.js`.

## Entry-Taper Self-Defeat and Grid-Quantization Alias

`_channelCrossingPoints`'s "grace zone" taper (added to give a bundled lane correction real flow-axis room instead of a zero-length kink — see `entry-taper-grace-zone.test.js`'s own docblock) reserves `min(stubLengthFor(stubReq), halfSpan)` units of flow-axis room, moving a leg's entry boundary away from the approach point's own coordinate, whenever `laneCount > 1` (a real cross-axis lane correction is needed).

Two bugs surfaced together, live, the first time a second line joined an existing `mode: force` channel (`laneCount` 1→2) with a tightly-packed obstacle field nearby:

1. **Self-defeating `entryAlreadyInside`**: this flag — "is the boundary fundamentally a cross-axis-only correction, so the leg's arrival hint should stay a soft guarantee rather than a hard axis-lock" — was re-derived from `entryFlow` *after* the taper moved it. Since the taper's entire job is to move `entryFlow` away from `approachFlow`, succeeding at that job always flipped `entryAlreadyInside` false, escalating the leg's own hint from a soft "don't reverse" guarantee to a hard `channel_axis` lock that's geometrically unsatisfiable for a leg ending on the same flow-axis row it travels — forcing exactly the kind of artificial there-and-back detour `entryAlreadyInside`'s own docblock already warned about, just never connected to the taper itself. Fixed by capturing `entryWasAlreadyInside` before the taper block runs and using that captured value, not a re-derived one.
2. **Grid-quantization alias with another line's own registered segment**: fixing (1) alone wasn't sufficient — the exact reported config still zigzagged. Root-caused via leg-level isolation: two different lines' own approach-leg rows can be only a handful of real units apart (e.g. 8 units), yet at a coarse `grid_resolution` this file's own TWO quantization functions over the same grid — `Math.floor` for a registered segment's own cell (`_buildCrossingCostGrid`) vs `Math.round` for the A* query side (`_computeGrid`'s `w2c`/`h2c`) — can disagree right at a cell boundary, aliasing two genuinely-distinct rows into the same grid cell. `_buildCrossingCostGrid`'s real, large "parallel-overlap" anti-stacking penalty then fires against another line's ordinary, correctly-un-exempt segment (genuinely outside the channel's own bounds — its own docblock already explains why broadening that exemption to a mate's *whole route* was tried and reverted for a different real bug, and this fix does not touch that exemption at all). Fixed by `_taperAliasesRegisteredSegment`: an all-or-nothing guard checked before the taper commits to its candidate — if any other line's registered same-direction segment (with real cross-axis overlap) would alias under the same two quantization functions, skip the taper entirely (fall back to the pre-taper coordinate) rather than search for an alias-free offset. This taper is purely cosmetic (real room for a rounder corner, never load-bearing for correctness), so a tighter fallback corner is strictly safer than a detour.

**First shipped scoped to bundle-mates only** (this channel's own `members`), on the theory the reported collision was specifically mate-to-mate — confirmed too narrow by an immediate live follow-up: the identical alias fired against a completely unrelated, non-mate line's segment that merely happened to sit one grid cell away. Since the false-positive-alias risk this guard exists to catch has nothing to do with mate status (`_buildCrossingCostGrid`'s own parallel-overlap penalty already applies to any other line's segment regardless), the guard now checks every registered segment. This broadening is safe against the same "don't broaden an exemption" precedent (1) cites — unlike `_buildCrossingCostGrid`'s own `regions` exemption, this guard never exempts anything from a real cost; it only ever chooses to skip a purely cosmetic taper, which can't make a route worse, only sometimes render a corner tighter than strictly necessary.

Covered by `tests/routing/channel-taper-grid-alias.test.js`. Both fixes are layered — (2) alone, without (1), would still leave the self-defeat bug live for any scenario where the taper's candidate happens not to alias with anything.

**A third live follow-up** surfaced the same alias class through a completely different code path: `_pushBundledApproachLegs`'s own `corridorOffset` computation (the mechanism that builds the `from→nudge→mid→to` split for ANY bundled approach leg, not just the taper) saturates fully against `available` — `|to[flow]-from[flow]|` — the exact same way the taper's own displacement does, whenever a real corridor boundary (not a taper) sits close enough to the approach point that the whole flow-axis crossing distance fits inside the first (`from,nudge`) leg alone. When that happens, `mid[flow] === nudge[flow]` **by construction** (`mid` literally copies `nudge`'s own flow coordinate) — the `(nudge,mid)` leg is *structurally* a cross-axis-only move, regardless of what triggered its `lastHint`. Two bugs, found together:

1. Whenever `midIsTo` (mid coincides with the true boundary `to`), that structurally-cross-axis-only leg was still handed the real `lastHint` unmodified — including a hard `channel_axis` lock when the outer boundary genuinely wasn't already-inside. The same "hard block incompatible with same-flow-coordinate endpoints" class `entryAlreadyInside` exists to prevent, just never connected to *this* leg's own geometry. Fixed by downgrading exactly like the `entryAlreadyInside`-true case already does at its own call site: a real `continuationDir` (still present on a `channel_axis` hint as supplementary info) softens to a reversal-only `continuation` block; otherwise fully unconstrained `geometry`.
2. That downgrade alone wasn't sufficient — a soft hint still lets A* *choose* the cheap-looking alias detour when the underlying cost bias is the real cause (the same lesson from fix (2) above). Fixed by reusing `_taperAliasesRegisteredSegment` at `_pushBundledApproachLegs`'s own `corridorOffset` computation: if the resulting `nudge[flow]` risks a grid-quantization alias, treat the leg as having no real bundling room to offer (`corridorOffset = 0`, falling through to a single unsplit leg) rather than commit to a coordinate that risks a false-positive "crossing" — the exact same all-or-nothing philosophy as the taper's own fix, since this nudge is likewise purely cosmetic.

## Corridor-Entry Nudge Extension for Genuine Bundle-Mate Conflicts

Reported live (the "Kelvin" ship base_svg config): four lines bundled through chained `channel_3`→`channel_2` corridors rendered with one member taking a pointless extra pair of bends (a "double dogleg") compared to its siblings' clean single jog into the shared corridor — and, at other `grid_resolution` values, an actual rendered crossing between the same two lines. Sweeping `grid_resolution` across `[8,16,24,32,40,48,64]` found no resolution where the scenario rendered cleanly, proving the bug was in the *kind* of check being done, not its coarseness.

**Root cause, confirmed via direct harness instrumentation**: `_pushBundledApproachLegs`'s `corridorOffset` (`stubLengthFor(stubReq) + laneIndex * lineSpacing`) has no awareness of *other* lines' own still-active approach segments. Whichever bundle member has the smallest `laneIndex` gets the smallest nudge distance — but if that small nudge lands at a flow-axis coordinate still within another member's own not-yet-turned approach run, the resulting cross-axis correction leg genuinely crosses that other line's segment. The pathfinder then correctly detours around this **real** conflict, but via an inelegant, multi-bend workaround instead of simply extending the nudge far enough to clear the conflict in the first place.

**Two generic fixes were tried first and are worth recording so they aren't re-attempted:**

- A post-search short-circuit (`_maybeStraightenPureCrossAxisLeg`, near `_distanceToNearestOtherLineSegment`): for a leg whose endpoints already share a coordinate on one axis with both hints fully soft (`'geometry'`/`'continuation'`), compare the search result against the trivial 2-point straight line and take it when safe (`_segmentCrossesObstacle` plus a new real-geometry proximity check, `_pureCrossAxisLegTooCloseToOtherLine` — no grid cells involved). **Shipped, zero regressions** — but confirmed, via direct instrumentation of the reported scenario, that it does **not** fix the reported case: the safety check correctly detects that the straight line really would cross another line's approach leg there and declines to fire. (A parallel-only relaxation of that same check — on the theory that a single perpendicular crossing between bundle-mates is normal, tolerated geometry, mirroring `perpMates`'s own design intent — was tried and confirmed to reintroduce the exact crossing the original detour was preventing; reverted.)
- Generalizing the same short-circuit to hard `channel_axis`-hinted legs (when the leg's own single straight-line axis already matches the hint's required axis, the constraint is trivially satisfied). **Reverted**: confirmed to measurably change real corridor-vs-plain cost comparisons elsewhere (regressed `diagonal-segment.test.js` and others) — this leg shape sometimes participates in a genuine cost decision, not just cosmetic shape, so straightening it isn't purely additive the way the soft-hint-only version is.

**Actual fix, at the nudge's own source**: in `_pushBundledApproachLegs`, after `corridorOffset` is computed (and after the existing `_taperAliasesRegisteredSegment` alias guard), if the resulting `(nudge, mid)` leg would run unsafely close to another line's already-registered segment, extend the offset in `lineSpacing`-sized steps — reusing `_pureCrossAxisLegTooCloseToOtherLine` — up to the same `available` clamp already in force, and take the smallest safe extension found. Purely additive: the common (already-safe) case is unaffected (the first check finds it safe immediately), and when no safe extension exists either, `corridorOffset` is left exactly as computed, so the pre-existing detour mechanism downstream is unaffected. Fixes the reported scenario cleanly (single jog, zero crossings) at `grid_resolution` 8/16/24/32/64; confirmed a genuine fixed point (byte-identical across independent runs, and with the discovery-pass cap raised to 20). `grid_resolution` 40/48 still exhibit a separate, unrelated detour deep inside `channel_2`'s own vertical run — not investigated as part of this fix; tracked as a `.todo()` in `tests/routing/kelvin-bundle-crossing.test.js`.

Covered by `tests/routing/kelvin-bundle-crossing.test.js`.

## Cross-Axis-Aware Corridor-Entry Nudge Sizing

Follow-up, reported live: even with no conflict at all, a bundled line's corridor-entry lead-in (the flow-axis run before its first turn) was visibly longer than it needed to be — `stubLengthFor(stubReq)` (`2 × corner_radius`) reserves flow-axis room sized for the *configured* `corner_radius` (e.g. 34), but the S-curve's own two corners at the lane-separation jog are actually constrained by the **cross-axis** lane-offset distance (`line_spacing`-driven, typically 8-12px), not `corner_radius` at all. Confirmed via `_estimateCornerRadii`'s own clamp (`min(radiusGlobal, legLength/2)`) plus its consecutive-corner fill-fraction: isolating a single bundled line showed its two jog corners achieving ~8.6px regardless of a 34px `corner_radius` target — entirely set by the ~26px cross-axis distance between lanes. Reserving flow-axis room for a radius these corners can never reach is real, measured waste.

**Fix**: in `_pushBundledApproachLegs`, cap the `corner_radius` used to size `rawOffset` at `min(corner_radius, crossDist * 0.325)` (`crossDist = |to[cross] - from[cross]|`, and `0.325` derives directly from the `0.65` consecutive-corner fill-fraction split evenly between the two corners sharing that cross-axis segment) — but **only when doing so doesn't change whether the reservation saturates against the leg's own `available` room**. A first version without that guard reintroduced a real regression: `_pushBundledApproachLegs` is called for BOTH a line's corridor entry AND its corridor exit (departure to its own true, unshared destination), and the exit case often *relies* on the old, larger reservation deliberately overshooting `available` — saturating so that `mid` coincides exactly with `to` (see `midIsTo` below), collapsing what would otherwise be a genuine 3-leg structure into a single clean corner. Shrinking the reservation there un-saturated it, flipping a 2-bend exit into a 3-bend one — caught by `channel-chain-transition-taper.test.js`'s own pre-existing "still 2 clean bends" assertion. The guard: compute the *legacy* `rawOffset` first; only substitute the smaller, cross-axis-derived one when the legacy value was already `< available` (i.e. wasn't relying on saturation in the first place).

Covered by `tests/routing/kelvin-bundle-crossing.test.js` (the shortened-lead-in case) and the pre-existing `channel-chain-transition-taper.test.js` (the saturation-guard regression).

## Uniform Bundle-Entry Radius via Reverse Curves

Follow-up to the section above, reported live (the "Kelvin" ship base_svg config, the same scenario `kelvin-bundle-crossing.test.js` is built from): the section above establishes that a bundle member's own lane-separation S-curve — rendered as a plain 90°-quarter-circle fillet — is capped at roughly `crossDist * 0.325`, entirely independent of `corner_radius`. `crossDist` itself is different for every member (four controls 50px apart converging onto lanes 8px apart), so the four entry S-curves rendered at visibly different, undersized radii even though `corner_radius` was configured identically for all of them — in sharp visual contrast to the SAME bundle's later channel-to-channel transition (e.g. `channel_3` → `channel_2`), which renders uniformly at the FULL `corner_radius` because every member has generous leg room there for an ordinary quarter-circle fillet. The two corners only *look* like "the same kind of turn": one is a converging funnel (inherently different `crossDist` per member, and a fundamentally different curve requirement), the other an ordinary corridor transition (identical turn magnitude for every member, just translated by lane).

**No config knob can fix this, and neither can cross-line radius coordination alone.** `corner_radius`, `corner_radius_mode`, `stub_length`, and `min_stub_length_factor` all govern how much flow-axis room gets *reserved* before a corner — none of them touch `crossDist`, which is what caps the achieved radius of a plain quarter-circle fillet. A first shipped revision of this fix reused the existing "Matched-Sibling Corner-Arc Clearance" convergence idiom (below) in the opposite direction — `Math.min` across a small sibling registry, tightening every member down to the group's smallest achievable quarter-circle radius — which was genuinely uniform, but reported live as still wrong: real HA testing showed every entry rendering as a small, sharp-looking 90° arc, since the whole group was now capped at whichever member had the tightest `crossDist`. The actual ask, once clarified, was "radius as close to the requested value as possible, for every member" — which a quarter-circle fillet on a short shared segment can never deliver regardless of coordination, because its radius is mathematically tied to how much of that segment it consumes (`r = min(radiusGlobal, legLength/2)`).

**Fix — a genuine reverse curve, not a coordination trick.** `reverseCurveGeometry` (module-level pure function, `RouterCore.js`, alongside `stubLengthFor`) computes the classic road/rail "S-curve lane-change": two tangent circular arcs of one shared radius `R`, connecting a flow-axis-aligned line to a parallel one offset by `d` (`crossDist`) on the cross axis. Identities: `d = 2R(1-cosθ)`, `L = 2R sinθ` (flow-axis length consumed, `flowHalf = R sinθ` per side), `θ` capped at 90° (beyond that the curve's own flow-direction component goes negative — a "hooked" S, not a clean lane change). A small `crossDist` therefore doesn't need a small circle — it sweeps a *smaller portion* (`θ`) of the SAME target radius, which is what makes every member converge on the same visible curve size without needing to know anything about its siblings at all: each independently targets `radiusGlobal` (the configured `corner_radius`), and gets it, provided there's enough flow-axis room. When `d > 2R` the excess (`dResidual`) is absorbed as a plain straight cross-axis segment between the two arcs — a continuous degrade into the old two-full-radius-fillets-plus-gap shape, not a separate code path. When the target radius doesn't fit the available room on either side, `R` is re-derived from the room constraint instead (`θ = 2·arctan(d / (2·Lavail))`, `R = Lavail / sinθ`) — shrinking gracefully toward a hard corner as room shrinks toward zero, never growing past `radiusGlobal`.

**Reservation**: bundle-entry legs (`_pushBundledApproachLegs`, gated on a truthy `bundleEntryHints` — see below) skip the old crossDist-based reservation shrink entirely (that shrink existed specifically because a plain quarter-circle fillet could never use more room than `crossDist*0.325` anyway — the reverse curve genuinely can, up to `flowHalf ≤ radiusGlobal` per side) and keep the full `stubLengthFor(stubReq)` (`2 × corner_radius`) reservation instead. Exit legs are completely unaffected — they still render as plain quarter-circle fillets and still use the original shrink.

**Identification and rendering**: `_pushBundledApproachLegs` already knows exactly which two points are the `nudge`/`mid` pair and which channel they belong to the moment it builds them, and pushes a lightweight hint (`{ nudge, mid, channelId }`) onto a `bundleEntryHints` accumulator threaded through `_computeCorridorRoutedAttempt`'s `meta` — populated **only at the entry-leg call site**, never the tail/departure call site (mirrors the reservation scoping above). `_buildBundleEntryReverseCurves` (`RouterCore.js`, called from `_applyCornerRounding` right after `_estimateCornerRadii`) matches each hint back onto `pts` by coordinate (not index — `_compactPolyline`/`_collapseSoftLegReversals` can shift indices; a hint whose `nudge`/`mid` no longer survives as adjacent points simply no-ops, leaving that corner to render exactly as it would without this feature), computes the reverse-curve geometry, and stores a `.reverseCurve` descriptor (T1/M1/M2/T2 tangent and inflection points, sweep flags, achieved R) on the two matched `cornerRadii` entries — consumed by a small dedicated branch in `_applyCornerRounding`'s render loop instead of the generic per-vertex quarter-circle path. `.radius` is also set to the achieved `R` for any other code reading it (e.g. crossing-clearance trim registration) — a reasonable approximation for a partial-sweep shape, since `R` still bounds how far the curve reaches into the segment.

**Deliberately NOT built on `_matchedTrunkCorner`**: that helper identifies a **trunk-EXIT corner** — one whose *incoming* segment's flow span exactly matches a line's own already-registered trunk *member* span (the far end of the channel's own registered through-run). A bundle-entry S-curve's `nudge`/`mid` points structurally never satisfy this — their flow spans are the tiny approach-leg jog itself, not the channel's own registered span.

**Shipped as the new default, not a config knob** — this can only ever make bundle-entry rendering closer to the configured `corner_radius` and more consistent than before, so there's no tradeoff a config flag would need to arbitrate.

Covered by `tests/routing/bundle-entry-radius-coordination.test.js` (every Kelvin member reaching the full configured radius, a room-constrained case rendering below target but still real, the channel-to-channel transition corner staying unaffected, convergence within the pass cap for both the Kelvin fixture and a larger synthetic bundle) and deliberately-updated pinned assertions in `tests/routing/kelvin-bundle-crossing.test.js` and `tests/routing/entry-taper-grace-zone.test.js` (both now reflect the full-target-radius outcome instead of the superseded crossDist-derived or group-clamped ones).

## Concentric Bundle-Entry Positions

**Follow-up, same live report: matching radii alone still wasn't "concentric."** Even with every member's entry S-curve now targeting the same radius, the bends started at visibly different flow-axis positions — a staircase, not a converging comb — because `_pushBundledApproachLegs`'s `corridorOffset` unconditionally added `laneIndex * lineSpacing` to every bundle member's nudge distance (see "Cross-Axis-Aware Corridor-Entry Nudge Sizing" above), regardless of whether anything actually required that separation. That term exists for a real, previously-confirmed reason (this function's own docblock: vertically-stacked, same-`anchor_side` controls whose stubs reach the same x would otherwise run visually coincident before diverging only in the final few pixels) — but the function *already* has a second, independent safety net for exactly this: the conflict-extension search just below (`_pureCrossAxisLegTooCloseToOtherLine`, "Corridor-Entry Nudge Extension for Genuine Bundle-Mate Conflicts" above), which re-derives however much separation a specific line actually needs, on demand, by testing its candidate `(nudge, mid)` leg against every currently-registered sibling segment. The unconditional `laneIndex` term was pure double-coverage for the common case, at the cost of staggering every member apart even when nothing required it.

**Fix**: `laneStagger = bundleEntryHints ? 0 : laneIndex * lineSpacing` — bundle-**entry** legs (identified the same way as the reverse-curve fix, via a truthy `bundleEntryHints`) start their conflict-extension search from a *shared*, unstaggered baseline instead of a pre-biased per-lane one; the extension search itself is completely unchanged and still runs exactly as before, now simply starting from a tighter initial guess. Bundle-**exit** legs (the tail/departure call site, `bundleEntryHints` always null there) keep the original, unconditional stagger completely untouched — exit-leg saturation (`midIsTo`) has its own documented, previously-regressed sensitivity to this term's magnitude, and this fix was deliberately scoped to never touch that leg.

Verified geometrically sound, not just empirically: for the Kelvin fixture, two of the four members (line_4, line_5 — whose own `crossDist` is small enough that their cross-axis jog never reaches far enough to pass through a sibling's still-straight approach row) land on the *exact same* unstaggered position. The other two (line_3, line_6 — the outermost rows, with the largest `crossDist`) still get pushed further out, correctly: their longer vertical jog would otherwise cut through line_4's or line_5's own still-horizontal approach leg at that shared x, a real conflict the extension search correctly detects and resolves by extending — not a leftover artifact of the removed unconditional stagger. The resulting spread across all four members is a small fraction of what the unconditional per-lane stagger produced (roughly 10 units vs. 50+ at the same fixture/resolution).

Covered by `tests/routing/bundle-entry-radius-coordination.test.js`'s own concentricity test (line_4/line_5 land on the identical position; the full group's spread is asserted well under the old unconditional-stagger magnitude) and a deliberately-updated pinned assertion in `tests/routing/kelvin-bundle-crossing.test.js` (`line_3`'s turn is no longer asserted strictly past `line_4`'s — landing on the exact same position is now the common, correct outcome).

## Chain-Aware Corridor Lane Consistency

**The user's own framing turned out to be exactly right**: lane assignment (`_trunkLaneAssignment`) decided which side/offset a line gets at a corridor **entirely locally, one corridor at a time**, with zero visibility into what the same line — or a sibling sharing that corridor — decides at any *other* corridor in a multi-corridor chain. Three targeted fixes earlier this session (`naturalSide` reference-point correction, the config-channel same-side tie-break, this section's own predecessor) each patched a symptom of that same gap without closing it; a real reported scenario (two lines chained through a horizontal channel then a vertical discovered trunk) still crossed after all three shipped. This is the architectural fix, split into the same two problems a PCB/FPGA router's global-routing/detailed-routing split would separate: one line disagreeing with its own chain (Phase 1), and two different lines' relative order failing to compose (Phase 2).

### Phase 1 — Chain Self-Consistency Propagation

The full chain of corridors a line will traverse is known up front (`chainChannels`, built by `_mergeCorridors` before any per-corridor lane decision runs) — a previously-unused architectural opening. `naturalSide`/`naturalLean`'s existing sign convention (negative cross-offset = north/west, positive = south/east) is **frame-fixed** — it doesn't rotate with direction of travel — so two corridors' "positive" doesn't mean the same physical side of a bundle unless corrected for how travel direction differs between them.

`corridorFlowFactor(flowSign, horizontal)` (module-level pure function, alongside `stubLengthFor`) computes `k = flowSign × (horizontal ? +1 : -1)` per corridor per line. Given a line's real, locally-measured `naturalLean` at one **canonical** corridor in its chain (`_naturalLeanAt`, extracted unchanged from `_mergeOrRegisterTrunk`'s own `refPoint` logic), the chain-consistent target at any *other* corridor `B` is `offsetRel = naturalLean(canonical) × k(canonical)`, `targetLean(B) = offsetRel × k(B)`, `targetSide(B) = Math.sign(targetLean(B))`. No explicit "classify this turn as CW/CCW" step — that classification, if wanted, falls out as `Math.sign(k_A × k_B)`, but the implementation never reasons in that language directly: hand-derived clockwise/counter-clockwise reasoning produced a **wrong answer** during this mechanism's own design (an eastbound→southbound turn's crossing-free mapping is NORTH→EAST/SOUTH→WEST, not the reverse — caught and corrected before any code was written, by literally constructing both candidate polylines and checking for a real intersection, independently, twice). The closed-form `k`-factor formula sidesteps that error class entirely — verified via a table-driven test covering all 4 horizontal/vertical × east-or-west/north-or-south combinations, each checked against a literal constructed two-line crossing test, not just the formula agreeing with itself (`tests/routing/chain-side-propagation.test.js`).

Verified properties: same-axis chains degrade to identity (`k_A ≡ k_B`, no special-casing); the transform is its own inverse (propagating A→B then treating the result as B's own local lean and propagating back recovers the original exactly, since `k²=1` whenever `k` is nonzero); only a chain's first-or-last corridor can ever be a valid canonical anchor (an interior corridor has no adjacent raw endpoint — using one would resurrect the exact bug class `_naturalLeanAt`'s own `refPoint` selection already exists to prevent); a discovered trunk's own creator is excluded from having a side at all, unchanged; **magnitude never propagates, only sign** — a lean's magnitude is a physical distance in one corridor's own local frame, with no principled meaning translated to another corridor's frame (this is exactly why the same-side tie-break's magnitude comparison, Phase 2 below, needed its own separate mechanism rather than reusing this one).

`_chainSideAssignment(chainChannels, lineId, rawA, rawB)` orchestrates this, returning `Map<corridorId, {side, lean, offsetRel, k, grounded}> | null` (null for a single-corridor "chain" — deliberately *not* computed even trivially there; see its own docblock for why activating it broadly regressed a plain-vs-corridor cost comparison for solo discovered-trunk candidates, a blast radius far wider than intended). Computed once per `_computeCorridorRoutedAttempt` call (before the per-corridor leg loop), threaded as `chainSideHint` into every `_trunkLaneAssignment` call the attempt makes (`_channelCrossingPoints`' real entry/exit, `_corridorRefPoint`'s look-ahead — both must receive the *same* hint or the look-ahead and the real computation it's looking ahead from can disagree, reintroducing the overshoot-then-reverse bug class `_corridorRefPoint`'s own docblock documents fixing once) and recorded on the result's own `meta.chainSides` so `_registerLineSegments`/`_mergeOrRegisterTrunk` can register the *same* values just rendered with, not silently recompute a possibly-different one later. `_trunkLaneAssignment`'s `sideOf`/`leanOf` closures consult the hint only for the asking line itself — every other member's lookup is untouched.

**The member tuple grows from 5 to 7 elements**: `[flowLo, flowHi, naturalSide, cornerInfo, naturalLean, offsetRel, k]`. `naturalLean` stays each corridor's own unmodified local value (magnitude never propagates); only the discretized `naturalSide` is overridden when a chain hint applies. `offsetRel`/`k` are the propagation's own intermediates, persisted so Phase 2 (below) can later tell whether a member's side here came from real local geometry or from propagation. Both fold into the existing idempotence change-guard alongside `naturalSide`/`naturalLean`/`cornerInfo`.

**Canonical lean uses the canonical corridor's own reference endpoint DIRECTLY — never re-derived via `_naturalLeanAt`'s own "closer of `rawA`/`rawB`" distance comparison.** That comparison is correct for `_mergeOrRegisterTrunk`'s own per-RUN use (its corridor argument is always a specific line's own about-to-be-registered SPAN), but was initially reused, incorrectly, for the canonical-lean computation too — a real, live regression caught in HA testing, not the synthetic suite: `_chainCanonicalIndex` already resolves which raw endpoint is structurally adjacent to the canonical corridor (index 0 is always `rawA`, the last index always `rawB`) — but `_naturalLeanAt`'s own independent re-derivation of that same choice compares against the canonical corridor's `x1/x2/y1/y2`, which for a **discovered trunk** are the union of every member's registered span. For the trunk's own creator, that's its full end-to-end run — often far longer than a joiner's own local traversal through it. Reported live (the "Kelvin" `line_2`/`line_7`/`channel_4` scenario this mechanism was built against): `line_7` chains through `channel_4` then organically joins a vertical trunk `line_2` itself creates; `line_7`'s own anchor (never actually near that trunk) read as "closer" to the trunk's oversized bounds than its real, locally-relevant destination did, joining it on the wrong side and forcing it to cross back over `line_2`'s own line. An authored config channel's bounds are stable/user-configured, not skewed this way, which is why the bug didn't surface in `kelvin-bundle-crossing.test.js`'s own scenario (chained through two authored channels, never a discovered trunk) despite that scenario exercising Phase 1 end-to-end. Confirmed via the real pipeline: 2 rendered crossings before the fix, 0 after, `line_7` correctly riding the destination-side lane (`tests/routing/chain-self-consistency-regression.test.js`, `tests/routing/chain-side-propagation.test.js`'s own dedicated pure-helper reproduction).

### Phase 2 — Cross-Line Chain Consistency

Phase 1 makes one line's own `naturalSide` chain-consistent. It says nothing about **two different lines**, each individually self-consistent, whose relative order at a shared corridor might not compose with their relative order at another corridor they also both share — the same-side tie-break's magnitude comparison (`Math.abs(leanOf(a)) − Math.abs(leanOf(b))`, both `_trunkLaneAssignment` branches) is exactly where this bites, since it compares two lines' `naturalLean` values directly, with no notion of whether either is even measured in a trustworthy frame at that corridor.

**Two candidate architectures were proposed and rejected before this one, on record so they aren't re-attempted:**

- **Group-wide canonical anchor** (one shared anchor for a whole tie-break group, instead of each line picking its own): fails because "shares a second, differently-oriented corridor" is a pairwise relation with no general transitive closure across 3+ lines (A–B share Y, B–C share Z, A–C share nothing — no group-wide anchor exists). Even restricted to a well-defined pair, deriving a value at a corridor a line doesn't touch requires the same unprincipled magnitude-translation Phase 1 already declined to do.
- **Iterative detect-and-correct** (use Phase 1's propagation as a default, validate against literal rendered geometry after each discovery pass, force-flip any inconsistent pair): the detection half is sound and is what this mechanism's own test suite uses to verify correctness. But a flip rule that reads the *other* line's current registered state is structurally the same shape as an already-reverted mechanism in this file (Matched-Sibling Corner-Arc Clearance's own history: an excludes-and-replaces cross-referenced correction confirmed to oscillate, "cycling between ~2.7 and ~34 indefinitely"). A safe flip rule would need to be a pure function of stable, pass-independent facts — at which point it's no longer an iterative loop, it's an analytical rule with a geometry check bolted on, and would also require new persistent per-pass state (a real, unjustified departure from "derived, never stored").

**The shipped design reuses Phase 1's own discipline one level up** — one grounded reference frame, sign/topology propagated via a closed-form ±1 factor, magnitude never propagated — applied to a *pair* of lines instead of one line's own chain:

1. **Groundedness gate** (`_bothGroundedAt`, `_locallyGrounded`): a corridor's own recorded `naturalLean` magnitude for a member is safe to compare against another member's ONLY when it's that member's own chain's canonical anchor (`grounded`, from Phase 1's member tuple). Combines two checks, not one: the stored `grounded` flag (catches a line ungrounded here because its own canonical anchor is a corridor the OTHER line never touches at all — a case the original co-occurrence-only check couldn't see), **and** the original same-side safety check (`_coOccurringOtherCorridors`: do the two lines also co-occur, as members, in some other differently-oriented corridor) kept as a structural floor underneath it. The floor is necessary, not redundant: `grounded` can only be accurate when a line's registration ran through the real `_chainSideAssignment` pipeline, and every hand-built unit test in this suite that calls `_registerLineSegments` directly (bypassing `computePath`) has no `chainSides` at all — `grounded` silently defaults to `true` there, which the co-occurrence floor catches. Confirmed as a real gap, not hypothetical: `channel-lane-natural-side.test.js`'s own dedicated regression test for this exact scenario failed the moment the flag-only version briefly shipped. Applied uniformly to **both** `_trunkLaneAssignment` branches — previously the discovered-trunk branch's own equivalent comparison (`withinGroupCmp`) had **no safety gate at all**, an asymmetry confirmed live and closed here alongside the harder cross-line problem, not as a separate patch.
2. **Seed-and-propagate** (`_pairwiseCrossCorridorOrder`), when the corridor itself isn't jointly grounded: among the other, differently-oriented corridors the pair co-occurs in, the seed must be one where **both** lines are locally grounded (`_locallyGrounded` — deliberately not `_bothGroundedAt` again here, which would recursively find the corridor being tie-broken itself as a disqualifying co-occurrence relative to the seed, making this a permanent no-op). Exactly one such candidate is required — zero means no defensible seed, 2+ is a genuine, unresolvable tie — both fall through to lexicographic, identical to today. The pair's order at the seed (`Math.abs(leanAtSeed(A)) − Math.abs(leanAtSeed(B))`, now justified since both are grounded there) maps to the target corridor via a binary handedness factor:
   ```
   pairOrderHandedness(kASeed, kATarget, kBSeed, kBTarget) = sign((kASeed·kATarget) × (kBSeed·kBTarget))
   orderAtTarget = orderAtSeed × handedness
   ```
   Purely topological (±1, never a magnitude), reusing the exact `k` values Phase 1 already computes and stores — one formula, two call sites. Because every `k` is ±1, this composes across any chain length for free — an intermediate corridor's `k` cancels out of the direct seed→target product, no per-hop composition logic needed.

**Explicit hedge, stated as plainly as Phase 1's own N→E/S→W correction**: `pairOrderHandedness` is a hand-derived hypothesis, structurally consistent with Phase 1's algebra but not provable by algebra alone — this file's own history (the wrong CW/CCW derivation above, corrected only by literally constructing polylines) is a direct warning against trusting sign algebra like this without that check. It was verified the same way: run through the real routing pipeline on a constructed adversarial scenario (two ordinary config-channel joiners, chained through the identical two corridors, engineered so their real, grounded magnitude at the seed corridor disagrees in order with their untrusted local magnitude at the corridor being tie-broken) — confirmed a **real rendered crossing present with today's lexicographic-only fallback resolves to zero** once the mechanism is live, and a discovered-trunk analogue of the identical shape confirms it independently of corridor origin (`tests/routing/pairwise-cross-corridor-order.test.js`).

**A real regression was found and fixed before this shipped**: an unconditional version (no group-size restriction) produced **6 real crossings** in the "Kelvin" 4-line bundle (`kelvin-bundle-crossing.test.js`'s own scenario, all four members same-side at `channel_3`) — different pairs within the same 4-line bucket resolved via different, mutually-inconsistent seeds, and `Array.prototype.sort`'s comparator contract requires a transitive, consistent order across *every* element being sorted, which independent pairwise resolutions have no guarantee of composing into once 3+ lines share a bucket. `_sameSideOrder` (the shared comparator both `_trunkLaneAssignment` branches now route through, replacing two independently-drifting copies) takes a `groupSize` parameter and only attempts `_pairwiseCrossCorridorOrder` when it's exactly 2 — for exactly 2 lines there's only one pair, so transitivity across a 3rd/4th element is vacuous, and the restriction costs nothing there. A genuine fix for the 3+-line case would need a real constraint-satisfaction pass instead of a pairwise comparator — out of scope here, tracked below as a known limitation, not attempted.

`_bothGroundedAt`/`_pairwiseCrossCorridorOrder`/`_sameSideOrder` should **stay permanently**, not be retired once trusted — they're the correct degrade for tied/absent seed groundedness, both-ungrounded pairs, and genuinely cyclic 3+-way conflicts no pairwise mechanism can resolve; costs nothing to keep, matches the Matched-Sibling precedent's own validated lesson (keep the old safe mechanism running underneath, only let the new one improve on it once independently proven).

**What this does not handle**: tied/absent seed groundedness (falls back to lexicographic, no worse than today); 3+-way mutual (Condorcet-cycle-shaped) conflicts, inherent to pairwise comparator sorting, not resolved by trying harder within this design; the handedness formula's correctness beyond what's been directly verified (treated as the largest residual risk, gated so a wrong result degrades to today's exact behavior rather than shipping silently wrong); ambiguous canonical-chain-end cases, inherited from Phase 1's own scope. Grid resolution/quantization was checked directly and found unrelated — every input to both phases (raw anchors/destinations, corridor bounds, `_channelCrossingPoints`' entry/exit points) operates on real, non-grid-snapped coordinates; grid snapping only happens in the Post-Search Reshape pass, downstream of all of this.

Covered by `tests/routing/chain-side-propagation.test.js` (Phase 1, pure-helper level, hand-built fixtures, literal-geometry-verified turn-handedness table), `tests/routing/pairwise-cross-corridor-order.test.js` (Phase 2: adversarial fixture, real-pipeline crossing resolution, discovered-trunk analogue, groupSize regression guard, convergence), `tests/routing/chain-self-consistency-regression.test.js` (Phase 1 confirmed active in the real Kelvin fixture).

## Convergence Discipline

The discovery loop only terminates affordably because of three invariants — every one was violated at least once by a "delete-then-recreate" or "stored assignment" pattern before being fixed:

1. **Idempotence**: re-registering identical geometry must not report a change (no purge-before-register anywhere in the routine flow).
2. **Derived state**: anything computed *from* the registries (lanes, band widths, lane counts) is recomputed from current state, never incrementally mutated.
3. **History independence**: `setOverlays` with a changed overlay set resets the discovered registries (channels re-seed from config). Bundle arrangements can be genuine cost ties with multiple stable outcomes — whichever line routes first picks the winner — so each config's outcome must be a function of the config plus the fixed loop order, never of edit history.

The regression suite encodes these directly: the fixed-point test (cache-cleared recompute reproduces the converged answer with zero version bumps) is the canary for the whole class.

**Debug forensics**: each cache entry's key embeds the `_registryVersion` it was stored at (`…|RV:n`), so `[...router._cache.keys()]` reconstructs the order lines were actually computed in — how the discovery-loop no-op bug was diagnosed live. `RouterCore.prototype.trunks()` (wired to `window.lcards.debug.msd.routing.trunks(cardId)`) snapshots every trunk row — id, origin, direction, `sourceLineId`, `creatorNaturalSide`, bounds, `crossCenter`, member ids — for inspecting bundling state without reaching into private fields; the MSD Studio dialog's "Discovered Trunks" canvas overlay reads the same method live. Every `computePath` result also carries `meta.debug: { stubLength, gridResolution, cornerRadiusMode, cornerRadius }` — the router's own resolved values for that specific line, computed once right before caching, useful for confirming what a `stub_length`/`corner_radius_mode` override actually resolved to without re-deriving it by hand.

## Pitfalls

- `grid_resolution` values ≤ 4 are silently coerced to 32.
- `channels` config lives at `msd.channels`, not `msd.routing.channels` (`MsdCardCoordinator` assembles RouterCore's config as `{ ...mergedConfig.routing, channels: mergedConfig.channels }`).
- Never call `computePath` with endpoints other than the line's real resolved anchors "just to inspect" — registration is a side effect of routing, and synthetic requests pollute the registries under the real line's id. `RouterCore.inspect(id)` reads the cache without computing.
- `route: direct`/`manual` results still register — intentional (walls/backbones participate in avoidance and bundling) — but they never *react* to other lines.
- Never derive bend/segment counts from raw `pts.length` — always `_compactPolyline(pts).length`; see Post-Search Reshape above.
- A channel with no `discoverable: false` is joinable by *any* nearby `auto`/`smart`/`grid` line, not just ones listing it in `route_channels` — a real, reported source of confusion ("why did an unrelated line's route change when I added a channel it isn't configured for") that isn't a bug, just the automatic-bundling design; see Trunk-and-Branch above.

## Known Limitations (deliberately not fixed)

Each of these was investigated with a concrete attempted fix, not just noticed and left:

- **`trunk_proximity` is a hard cutoff** (`_discoverTrunkCandidates`), not a graduated cost — a line either qualifies to bundle with a nearby trunk or it doesn't, with a real, measured cliff right at the threshold (confirmed: gap=32 succeeds at one cost, gap=33 fails outright, in the same scenario). Widening the gate (`* 2`) was tried specifically to soften this; it fixed the synthetic cliff case but caused a live, previously-correct scenario to regress to its exact pre-fix buggy shape (byte-identical coordinates). Reverted in full. A real fix needs the proximity check to contribute a graduated cost rather than a boolean gate, which changes the shape of the A* cost landscape broadly enough to warrant its own dedicated regression pass — deferred, not attempted further this round.
- **`_mergeCorridors`'s chain-ordering** sorts a line's candidate trunks by comparing each trunk's own flow-axis coordinate against that trunk's own flow span — a fine proxy when every chained trunk shares the line's dominant travel axis, but incomparable when a chain mixes a horizontal and a vertical trunk. Confirmed via direct trace (`scale-stress.test.js`'s `manyToOne` scenario) to occasionally order a provably-farther crossing point before a provably-closer one, forcing a real (if small) backtrack. Only reproduces in stress scenarios with several chained mixed-axis trunks, not realistic single-digit-line configs. Left as a tracked `.todo()` — a correct fix needs a genuinely different ordering metric (e.g. actual predicted crossing-point distance per candidate) verified for convergence/stability, which is a bigger change than this specific rare shape justifies right now.
- **Bend-count vs. corridor-discount cost weighting**: no clean, currently-reproducible case remains where the cost model visibly prefers a bundled route with excess local bends over a cleaner unbundled one purely due to weighting (as opposed to the now-fixed diagonal-reshape and bend-miscounting bugs, which were producing that appearance for unrelated reasons). `trunk_bundle_discount_cap` already bounds the theoretical worst case architecturally. Not pursued further absent a live repro.
- **Arc-vs-arc clearance between two arbitrary (non-bundle-mate) lines** whose corners happen to land near each other — as opposed to bundle-mates turning the same way, which Matched-Sibling Corner-Arc Clearance (above) solves exactly. Two attempts this session (candidate-center vs. a neighbor's registered arc, as a bounding box then as sample points — see `tmp/ROUTING_ARC_CLEARANCE_FOLLOWUP.md`) were tried and reverted: both are a sufficient-but-not-necessary safety proxy that gets measurably wrong once the target is a discrete curve. The bundle-mate fix works specifically because a matched sibling's exact resolved geometry is already known and looked up, not searched for; two unrelated lines have no such shared registry key to key that lookup on, so the same exact-sampling technique doesn't generalize without a real "which lines are worth comparing" discovery mechanism of its own. Deferred, not attempted further.
- **`_buildCrossingCostGrid`'s `overlapRegions`/`perpMates` formulas are confirmed too pervasively load-bearing to edit directly.** Investigated at length this session while chasing the Corridor-Entry Nudge Extension bug (above) before the actual fix was found to live elsewhere: four distinct modification strategies for `overlapRegions` alone (binary cell-span widening, exact-segment-coordinate hybrid, consistent floor-quantization, and a fully "correct" proportional-overlap-fraction fill) each regress the full test suite, in different combinations of files every time (up to 8 tests across 4 files for the most "correct" version). Rescoping `perpMates` directly is worse: 15 regressions across 11 files, including both of `convergence.test.js`'s own fixed-point tests — this mechanism is load-bearing for the discovery loop's convergence guarantee itself, not just cosmetic shape. If a future crossing/detour bug seems to trace to either mechanism, look for a narrow, additive, upstream-of-the-cost-grid fix instead (the Corridor-Entry Nudge Extension section above is the template) rather than editing these formulas in place.
- **`_pairwiseCrossCorridorOrder`'s cross-line consistency mechanism (see Chain-Aware Corridor Lane Consistency above) is deliberately restricted to exactly 2 same-side lines at a corridor.** A same-side group of 3+ has no such restriction-free fix within a pairwise-comparator architecture: `Array.prototype.sort` requires a transitive, consistent order across every element being compared, but independent pairwise resolutions (each potentially via a different seed corridor) have no guarantee of composing into one. Confirmed as a real, reproduced regression during this mechanism's own development (6 crossings in the "Kelvin" 4-line bundle) before the `groupSize === 2` restriction was added. A genuine fix would need a real constraint-satisfaction pass over the whole same-side group at once, not a comparator — a materially bigger change than this pass's own scope, not attempted.
